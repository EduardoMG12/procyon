# 0001 — v0.1: Lint the Spec

> Status: **done** (v0.1.0) · Depends on: nothing · Vision: [0000](0000-vision.md)

## Goals

Read a spec and report the security problems in the API's design, with no
running API involved. Useful on its own, fast enough for every PR, and the
foundation v0.2 builds on.

Done means: in a repository with an OpenAPI spec,

```sh
procyon lint openapi.yaml
```

prints every finding with its file, line and column, why it is a risk and how
to fix it, and exits `1` when a finding is `high` or worse. The same run can
write SARIF for GitHub code scanning and Markdown for the job summary. An
operation that is public on purpose is marked in the spec once, with a
reason, and stops failing the build. Nothing more.

## Requirements

### Input
- [x] Accepts OpenAPI 3.0 and 3.1, in YAML or JSON.
- [x] Accepts Swagger 2.0 by converting it to OpenAPI 3.0 internally. Findings
      still point at the right line and column of the **original** Swagger
      file (the converter drops locations; see *Risks*).
- [x] Follows `$ref`s to other local files. A finding inside a referenced file
      points at that file.
- [x] Refuses `$ref`s to URLs with a clear error. Linting never touches the
      network.
- [x] An unreadable file, invalid YAML/JSON or an invalid spec prints a
      one-line error that says what is wrong and where, and exits `2`. No
      panic, no stack trace.

### Rules

Every rule is deterministic, has a page in `docs/rules/PRCxxx.md` (what it
catches, why it matters, how to fix it, how to ignore it, a bad and a good
example) and is tested against specs that must trigger it and specs that must
not.

| ID | Finding when… | Severity | OWASP API 2023 |
|---|---|---|---|
| PRC001 | An operation has no security requirement (neither its own nor the global one, or an empty `security: []`) and is not a public operation | high | API2 Broken Authentication |
| PRC002 | A security requirement names a scheme that is not defined in the spec | high | API2 |
| PRC003 | A security scheme is weak: an API key sent in the query string, or HTTP Basic | medium | API2 |
| PRC004 | A server URL uses `http://`. Loopback hosts (`localhost`, `127.0.0.1`, `[::1]`) are exempt | high | API8 Security Misconfiguration |
| PRC005 | A response schema contains a sensitive field | high | API3 Broken Object Property Level Authorization |
| PRC006 | An operation reachable without authentication (public or not) returns a PII field | high | API3 |
| PRC007 | An operation reachable without authentication (public or not) has a path parameter that identifies an object (`{id}`, `{userId}`, `{orderId}`, …) | high | API1 Broken Object Level Authorization |
| PRC008 | Unbounded input or output: a request body string without `maxLength` or array without `maxItems`, or a `GET` returning a top-level array with no paging parameter | low | API4 Unrestricted Resource Consumption |
| PRC009 | A request body lets the client write a privileged field (`role`, `isAdmin`, `permissions`, `scopes`, …) that is not `readOnly` | medium | API3 (mass assignment) |
| PRC010 | An authenticated operation under an admin-like path segment (`admin`, `internal`, `debug`, `management`) uses exactly the spec's default security, with nothing stricter of its own | medium | API5 Broken Function Level Authorization |
| PRC011 | An OAuth2 scheme offers the `implicit` or `password` flow | medium | API2 |

Notes:
- [x] The sensitive-field and PII word lists are curated, live in one place,
      cover English and Portuguese names (`password`/`senha`, `cpf`, `phone`/
      `telefone`), and match whole words inside camelCase, snake_case and
      kebab-case names (`userEmail` matches `email`; `emailVerified` does
      not count as PII because it is a boolean). Each list change comes with
      tests.
- [x] Findings from PRC006 and PRC007 still appear on public operations: a
      public operation that exposes PII or addresses objects by ID is the
      riskiest kind, and marking it public must not hide that.
- [x] No v0.1 rule emits `critical`; it is reserved for v0.2 runtime findings
      (something proven exploitable, not only badly designed).

### Public operations and ignores

Both live in the spec, on the operation, next to what they describe.

```yaml
paths:
  /health:
    get:
      x-procyon-public: "Load balancer health check, returns no data"
  /reports/{id}:
    get:
      x-procyon-ignore:
        - rule: PRC008
          reason: "Report size is capped by the database view"
          expires: 2027-01-31   # optional
```

- [x] `x-procyon-public` takes a non-empty reason string. It satisfies PRC001
      only.
- [x] Each `x-procyon-ignore` entry needs `rule` and a non-empty `reason`;
      `expires` (a date) is optional. A missing reason, an unknown rule ID or
      a malformed date is an input error (exit `2`): a typo must never
      silently ignore something.
- [x] A finding matched by an ignore becomes an ignored finding: still in
      every format, in its own section, never failing the run.
- [x] An expired ignore stops matching: the finding counts again and the
      report says the ignore expired on that date.
- [x] An ignore that matches no finding is reported as a note ("stale
      ignore"), so dead ignores get cleaned up. Notes never fail the run.

### Severity and exit codes
- [x] `--fail-on <critical|high|medium|low>`, default `high`.
- [x] Exit `0`: no finding at or above the fail threshold. Exit `1`: at least
      one. Exit `2`: usage or input error (nothing was linted).
- [x] An optional `.procyon.yaml` in the working directory may set
      `fail-on` and default formats. Flags win over the file. It holds no
      ignores: those live in the spec.

### Formats
- [x] `terminal` (default): grouped by severity, coloured when stdout is a
      terminal and plain otherwise (`NO_COLOR` respected). Each finding shows
      rule ID and title, `file:line:column`, the offending spec lines, why it
      is a risk, how to fix it and a link to the rule page. Ends with a
      one-line summary.
- [x] `json`: the full report, with a documented, versioned shape
      (`"version": 1`) that scripts can rely on.
- [x] `sarif`: SARIF 2.1.0 that GitHub code scanning accepts. Severity maps to
      SARIF `level`; ignored findings are emitted as suppressed results with
      their reason.
- [x] `markdown`: a summary table and the findings, suitable for
      `$GITHUB_STEP_SUMMARY`.
- [x] Several formats in one run: `--format terminal` for stdout plus
      `--output sarif=procyon.sarif --output markdown=summary.md`.
- [x] Formats only render a report. They never decide what is a finding.

### Distribution
- [x] Prebuilt binaries for Linux, macOS and Windows (amd64 and arm64) on each
      GitHub release, plus `go install`.
- [x] `procyon --version` prints the version and commit.
- [x] The README shows a copy-paste GitHub Actions job that runs Procyon and
      uploads its SARIF.

## Testing

- The main seam is the library entry point: spec files in, report out. Most
  tests are table tests over small fixture specs: "this spec produces exactly
  these findings at these locations". Rules are tested through that seam,
  not by calling rule internals.
- Formats are tested with golden files: a fixed report in, the exact bytes
  out. SARIF output is also validated against the SARIF 2.1.0 schema.
- The CLI is tested end to end for exit codes, flag handling and error
  messages.
- A corpus of real public specs (well-known open APIs, checked into
  `testdata/` with their licenses) runs in CI. It catches crashes and makes
  noise visible: a rule change that adds many findings across the corpus
  needs a justification in its PR.
- CI on Linux, macOS and Windows: `gofmt`, `go vet`, `staticcheck`,
  `go test -race`.

## Risks

- **Swagger 2.0 locations.** The converter produces an OpenAPI 3.0 document
  with no locations. Procyon must map elements of the converted document
  back to the original file (both are addressed by similar JSON pointers).
  Explored in its own ticket before it is promised in the README.
- **Word-list noise.** PRC005, PRC006 and PRC009 depend on field names. They
  are the rules most likely to be noisy; the real-spec corpus is the guard.

## Out of scope for v0.1

- Anything that sends HTTP requests (all of v0.2).
- Linting only the operations changed in a PR (v0.2).
- Posting PR comments through the GitHub API (v0.2). The Markdown format plus
  the job summary covers v0.1.
- Reading specs from URLs (v0.3).
- A baseline file that accepts all existing findings at once. Ignores are
  per operation and per rule, with a reason, on purpose; a baseline is
  reconsidered if adoption on large existing specs proves painful.
- User-defined rules or plugins.

## Discoveries

Learned while building v0.1 (2026-10-24). Each was decided in its PR and
found or confirmed by review.

- **Locations.** kin-openapi records locations only when it parses YAML and
  tries JSON first; a trailing YAML comment makes JSON specs keep their
  locations. It records files as URLs (spaces become `%20`), translated back
  to the path as written. Its YAML syntax errors can be a line off, so
  syntax is checked first with goccy/go-yaml.
- **Validation.** Wrong `example`/`default` values never block a lint.
  Undefined security schemes on the global requirement and path operations
  are a finding (PRC002), not an input error; elsewhere they still stop the
  run. OpenAPI 3.2 URI-reference scheme names are not checked.
- **PRC005** reports tokens and API keys only in `GET` responses: a login
  returns a token by design. Deciding whether a field holds a value keeps a
  visited set, like the property walk: a self-referencing schema (a map of
  maps) overflowed the stack before.
- **PRC006** checks anonymous `GET`s only: a sign-up or login returns the
  caller's own data. Only text fields count as personal data.
- **PRC007** silences only through `x-procyon-ignore`, never
  `x-procyon-public`, matching the "public never hides" rule.
- **PRC010** compares an admin operation with regular operations (any
  order of alternatives and scopes), not only with the spec's default,
  which never fired on specs that repeat security everywhere.
- **Ignores** live on the element they excuse (operation, security scheme,
  server, OAuth2 flow, or the spec's root for the default requirement); the
  PRD's operations-only rule left scheme, server and flow findings
  impossible to ignore. Expiry lasts to the end of the date where Procyon
  runs.
- **`$refs`** read from one root, never follow symlinks, never read hidden
  files, and have size and count limits; seven review rounds and the threat
  model are recorded in `docs/refs.md`. A `ref-root` option was added.
- **SARIF** is not validated against the official schema in tests: its
  licence does not allow vendoring it; GitHub's requirements are checked
  instead.
- **Swagger 2.0** is converted with kin-openapi's converter, which keeps
  no locations. Each finding's location in the converted document is
  mapped to a JSON pointer, translated to the Swagger 2.0 pointer for the
  same element (`/components/schemas/X` → `/definitions/X`, a request body
  → its `body` parameter, or that entry's `$ref` when it refers to
  `#/parameters`, servers → `/schemes`) and looked up in the
  original file, falling back to the nearest ancestor. The converter copies
  a body or response schema once per media type; identical findings from
  those copies are reported once. Swagger 2.0 specs split across files are
  refused: the referenced files are 2.0 fragments the OpenAPI 3 loader
  cannot read. The converter also drops or blows up a few things, handled
  before or after it: operation-level `schemes` become
  that operation's servers; `$ref` on a path item is refused (it was
  dropped, so the path linted as clean); `consumes`/`produces` lists are
  trimmed to 8 media types (each one copies the whole schema); YAML aliases
  expanding past a limit are refused (decoding to JSON expands them;
  a long string counts its length); nulls where an object must be are
  refused with their line and column.
- **Benchmark against vulnerable and large real specs** (crAPI, VAmPI,
  Pixi, Juice Shop in the corpus; GitHub, Stripe, Kubernetes, Slack
  locally) changed several rules after the plan: a required credential
  *parameter* (`x-access-token`, `Authorization`) counts as authentication
  (#54); PRC008 also checks counts without a maximum (`limit`,
  `number_of_repeats`, #52); PRC005 reports secret values, not objects or
  enums that refer to them (#58); PRC009 skips a role assigned on purpose
  or limited to low values (#59); conflicting paths no longer stop a lint
  (#57); an ignore on one operation no longer hides a shared schema's
  finding for the others (#51). See [benchmark.md](../benchmark.md).
- **No baseline file**, as planned; ignores per element cover existing
  findings.
- **Word lists.** The sensitive-field and PII lists live together in
  `internal/lint/words.go` (#89). The privileged-field (PRC009) and
  admin-segment (PRC010) lists stay in their rule files: each belongs to one
  rule and is documented on its page.
- **Input errors.** A YAML syntax error, a bad ignore or `.procyon.yaml`
  points at a line and column; a spec that parses but is invalid (no
  `info`, a wrong type) is reported with its file and JSON pointer, since
  kin-openapi's validation errors carry no location.
