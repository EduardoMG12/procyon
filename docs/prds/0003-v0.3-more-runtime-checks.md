# 0003 — v0.3: More Runtime Checks

> Status: **draft**, decisions from the owner on 2026-10-31 · Depends on: [0002](0002-v0.2-runtime-tests.md) · Vision: [0000](0000-vision.md)

## Goals

v0.2 answers "can B reach A's object by its ID?" and "can an anonymous
caller reach what needs a login?". Running it against a real multi-tenant
SaaS backend on 2026-10-31 showed what it does not see yet:

- a **list or search** that hands B objects of A (a search filtered by a
  phone number returned every customer of the business);
- personal data in the answer of a **public** operation;
- **predictable IDs** where the ID is the only thing protecting a public
  link (the same "opaque" ID was given to a service, a car and an
  appointment, because they were each row 1 of their table);
- **internal errors** printed in the response (a PHP fatal error with the
  server's file paths).

v0.3 adds four checks for these. Each one works **with no configuration**
beyond what v0.2 already needs, in any language, because each one only
reads the HTTP answers Procyon already gets.

Done means: `procyon test` reports the four findings below on a vulnapi
endpoint planted for each, reports none on its fixed twin, and the
benchmark against VAmPI and crAPI adds no false positive.

## Requirements

### No new requests

- [ ] PRC106, PRC107 and PRC109 read only the responses `procyon test`
      already receives (A, B, anonymous, and the PRC103/PRC104 malformed
      requests). PRC108 adds B's calls to the list and search operations A
      already calls in discovery. No new kinds of request, no payloads.

### PRC106 — Public operation returns personal data

- [ ] An operation the **anonymous** caller reached (2xx) returns a field
      whose **name** is a personal-data word (the list `words` already
      keeps for PRC006) **and** whose **value** has that kind's shape: an
      e-mail address, a phone number, a national ID. `phone: null` or
      `email: ""` is not reported.
- [ ] The finding names the field, its location in the answer and the kind
      of data, with the value masked in the evidence.
- [ ] `x-procyon-ignore` can name a **field** of the response schema, with a
      reason, so a business's own public contact can be kept while any
      other personal field in the same answer is still reported.

### PRC107 — Predictable ID on a public operation

- [ ] An operation the anonymous caller reached takes an ID (path or query)
      that is **predictable**: a small sequential integer, or an opaque
      string Procyon saw for objects of **different types** (the same value
      as a service ID and a car ID).
- [ ] On an operation that needs a login, predictable IDs are not reported:
      PRC102 already tests whether another account can use them.

### PRC108 — Another account's list shows A's objects

- [ ] B calls every list and search operation A called. If B's answer
      contains an ID or a value only A's objects have (the oracle PRC102
      uses), it is a critical finding.
- [ ] A required filter is filled with **B's own** value (from B's
      responses), never A's: a search that ignores the filter is what
      leaks.
- [ ] This replaces the current behavior, where B seeing A's ID in a list
      only made Procyon skip the PRC102 test of that object.

### PRC109 — Internal error in the response

- [ ] Any response body with a stack trace or a database error is reported
      once per operation: PHP, Python, Java, Node, Go, .NET and Ruby
      traces, and SQL error texts (`SQLSTATE`, "syntax error at or near").
- [ ] The evidence shows the matched line, cut to a short length.

### Reporting

- [ ] The four rules have pages in `docs/rules/`, fixtures that must trigger
      and fixtures that must not, and vulnapi gets one planted endpoint per
      rule with its fixed twin.
- [x] An operation that anyone can read anonymously is never a PRC102
      (today it is: a public business page read by B was reported as
      critical).

## Out of scope for v0.3

- Configuration hygiene (security headers, CORS, debug routes): a later
  v0.3.x.
- Session checks (a token after logout, login attempts): a later v0.3.x,
  with the existing `login` block.
- Function-level authorization (a third, admin account) and mass
  assignment at runtime (generating request bodies).
- Sending new kinds of input to provoke errors.
- The permanent security-QA environment: now v0.4.

## Risks

- **Phone-shaped values.** An order number can look like a phone number.
  Requiring the field name too keeps this low; fixtures must show an
  `orderNumber` with eleven digits is not reported.
- **Public on purpose.** A business page shows the business's own phone.
  The field-level ignore is the answer; the rule page must say so first.
- **Shared values in PRC108.** A value both accounts have (a status, a
  plan name) must not count; PRC102's oracle already excludes values B's
  own responses contain.

## Discoveries

Learned while building v0.3. Each entry is added in the PR that found it.

- **An anonymous read is checked before B's** (#196). `testOperation`
  already called the anonymous caller with A's object in the path, so
  B's test is skipped when that read got a `2xx`, with no new request.
  crAPI's `GET /workshop/api/shop/orders/{order_id}` was a PRC101 and a
  PRC102 on the same anonymous hole; it is now the PRC101 only, and
  `benchmark.yml` asserts that.
