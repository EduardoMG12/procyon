# PRC109 — A response shows an internal error

| | |
|---|---|
| Severity | medium |
| OWASP API Security Top 10 | [API8:2023 Security Misconfiguration](https://owasp.org/API-Security/editions/2023/en/0xa8-security-misconfiguration/) |
| Found by | `procyon test` (runtime) |

## What it catches

`procyon test` reads every answer it already gets: A's and B's calls,
the anonymous ones and the malformed bodies of [PRC103](PRC103.md) and
[PRC104](PRC104.md). It sends nothing more for this rule. An answer, of
any status, that holds a stack trace or a database error is a finding,
once per operation: the first answer that shows it.

Only text the platform itself prints counts, so a message that says
"exception", or a field named `trace` that holds a request ID, is not
reported:

| What | Recognized by |
|---|---|
| PHP | `Fatal error: Uncaught`, `Fatal error: … .php on line`, `Stack trace:` followed by `#0` |
| Python | `Traceback (most recent call last)` |
| Java | `Exception in thread "`, a frame line `at ….method(File.java:12)` (or `Native Method`, `Unknown Source`) |
| Node.js | `at Object.<anonymous> (`, `at Module._compile (`, a frame line `at … /app/routes.js:12:9` |
| Go | `goroutine 7 [running]`, a line starting with `panic: ` |
| .NET | `System.Exception`, `System.…Exception`, a frame line `at … in ….cs:line 27` |
| Ruby | `….rb:12:in `, `(most recent call first)` |
| Database | `SQLSTATE[`, `syntax error at or near `, `You have an error in your SQL syntax`, `ORA-00933:`, `SQLite error`, `SQLITE_ERROR` |

A trace inside a JSON string (`"debug": "Traceback…\n  File…"`) is
recognized too: the body is read with JSON's escapes (`\\`, `\r`, `\n`,
`\t`, `\"`, `\/`, `\u003c`, `\u003e`, `\u0026`) undone, and Windows line
breaks made plain ones. The evidence is the exchange, with the text that
matched, to the end of its line, in place of the start of the body. It is
cut to 200 characters and every token is masked.

## Why it matters

A stack trace shows how the server is built: its file paths, its
framework and libraries, sometimes their versions, and the query that
failed. That tells an attacker where to aim, and a database error says
the input reached a query as it was, which is where SQL injection starts.

## How to fix it

Log the details on the server and answer with a short message and the
right status (`400` for bad input, `500` for a bug). Turn off the
framework's debug output in every deployment, the disposable copy
included: it is the same configuration that goes to production.

## How to ignore it

If the finding is fine on purpose, write an `x-procyon-ignore` on the
operation, with the reason. The finding is still reported, under
**Ignored**, and no longer fails the run. See
[ignoring a finding](../ignoring.md).

```yaml
/debug/echo:
  post:
    x-procyon-ignore:
      - rule: PRC109
        reason: "Debug route, only built into the test image"
```

## Known limits

- An answer is read up to its first 1 MiB.
- A trace in a format the table does not list (a custom logger, another
  language) is not recognized; neither is a database error worded by the
  application itself.
- An answer is reported as the first kind in the table it matches: one
  with both a PHP error and an SQL error is reported as the PHP error.
- The login a run starts with is not read: its answer holds the token
  that would have to be masked.

## Examples

Reported: a review whose rating is not a number, as A, and

```text
POST /reviews {"comment":"Clear and fast","rating":"not-a-number"}     (as A)
400 {"debug":"Traceback (most recent call last):\n  File \"/srv/app/reviews.py\", …
```

Not reported: the same request answered
`400 {"error":"rating must be a whole number from 1 to 5; comment at most 500 characters"}`.
