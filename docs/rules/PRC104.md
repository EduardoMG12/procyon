# PRC104 — Server accepted a request the spec forbids

| | |
|---|---|
| Severity | low |
| OWASP API Security Top 10 | [API8:2023 Security Misconfiguration](https://owasp.org/API-Security/editions/2023/en/0xa8-security-misconfiguration/) |
| Found by | `procyon test` (runtime) |

## What it catches

The same malformed bodies as [PRC103](PRC103.md) (a wrong type, a missing
required field, a value outside an enum, a string past its `maxLength`),
sent as test account A. A mutation that would equal the example is never
sent (a required field is only removed when the example has it). If one
gets a `2xx`, the server accepted what its own spec says it must refuse.

**A 2xx the spec documents as an error is a refusal.** Some APIs answer
a refused body with a 2xx, and say so in the spec: Pixi's login documents
`200` "successfully logged in" and `202` "successful request, but
invalid password". A 2xx is not counted as accepted when the operation
documents **another 2xx too** and this status's description holds an
error word: `error`, `invalid`, `fail`, `failed`, `failure`,
`already`, `missing`, `wrong`, `incorrect`, `denied`, `rejected`,
`refused`, `unauthorized`, `forbidden` (or their plurals). When the
spec's own example already gets such an answer, the malformed bodies are
not judged, and a note says so, as when it gets a `4xx`.

The 100 000-character string PRC103 sends where the spec sets no
`maxLength` is not judged here: the spec allows it, so accepting it is no
finding.

It is `low`: it does not fail the build with the default `--fail-on high`.

## Why it matters

What the server stores is not what the spec promises. A title of ten
thousand characters breaks the page that shows it; a missing field becomes
a `null` some other code does not expect; an unchecked type is where
injection and mass assignment start.

## How to fix it

Validate the request body against the schema (types, required fields,
enums, lengths) and answer `400` otherwise. If the spec is what is wrong
(the field is optional, the limit is higher), fix the spec.

## How to ignore it

If the finding is fine on purpose, write an `x-procyon-ignore` on the operation,
with the reason. The finding is still reported, under **Ignored**, and no
longer fails the run. See [ignoring a finding](../ignoring.md).

```yaml
/notes:
  post:
    x-procyon-ignore:
      - rule: PRC104
        reason: "Long titles are truncated by the database column"
```

## Examples

Reported: the schema says `title` is required, and

```text
POST /notes {"body": "x"}     (as A)
201 {"id":"4","title":"",...}
```

Not reported: the same request answered `400` or `422`, or `202`
when the spec documents `200` as the success and `202` as "missing
user or pass".

## Known limits

- A 2xx error answer the spec does not describe as one is still counted
  as accepted: an operation that documents only `200` ("the file, or an
  error message") and answers `200 {"message": "error: no file
  uploaded"}` is reported. The answer's body is not read: a word in it
  would be a guess about the server, the spec's description is the API's
  own word.
- The words are English, and a description that names an error it
  avoids ("saved, without errors") reads as an error.
