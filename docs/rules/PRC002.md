# PRC002 — Security requirement names an undefined scheme

| | |
|---|---|
| Severity | high |
| OWASP API Security Top 10 | [API2:2023 Broken Authentication](https://owasp.org/API-Security/editions/2023/en/0xa2-broken-authentication/) |

## What it catches

A `security` requirement, on the whole spec or on an operation, that names a
scheme not defined under `components.securitySchemes`. Usually a typo
(`apikey` instead of `apiKey`) or a scheme deleted while operations still
use it.

Strict OpenAPI validators reject such a spec outright. Procyon reports it as
a finding instead, pointing at the `security` field and naming the scheme,
because what it means in practice is a security problem: the protection the
spec documents does not exist.

## Why it matters

Clients, SDKs and API gateways generated from the spec cannot authenticate
against a scheme that is not defined. Gateways that enforce the spec may
skip the check altogether. And nobody reading the spec can tell how the
operation is really protected, or whether it is.

## How to fix it

Define the scheme, or correct the name to match one that is defined:

```yaml
security:
  - apiKey: []
components:
  securitySchemes:
    apiKey:
      type: apiKey
      in: header
      name: X-API-Key
```

## Examples

Reported (`token` is never defined):

```yaml
security:
  - token: []
```

Not reported: every name in every requirement is defined.
