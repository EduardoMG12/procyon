# PRC009 — Client can write a privileged field

| | |
|---|---|
| Severity | medium |
| OWASP API Security Top 10 | [API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/) (mass assignment) |

## What it catches

A request body field that grants privileges and that the client is allowed
to send: not `readOnly: true` (on the field, or on one of its `allOf` parts,
which is how OpenAPI 3.0 makes a `$ref` read-only), and not inside a
read-only object. Request bodies are checked through nested objects,
`allOf`/`oneOf`/`anyOf` and `$ref`s.

A field grants privileges when its name's head word is one of *role, admin,
administrator, superuser / super user, permission, privilege, scope, tenant*
(or the Portuguese *papel, administrador, permissão, privilégio*, with or
without accents), or its plural, optionally followed by an identifier word
(*id, uuid, name, code, key, slug, type, level, list*, and plurals).

Not checked, on purpose:

- **Items of arrays.** A list of child records, such as chat messages with a
  `role`, is not the record being assigned. A privileged array field itself
  (`permissions: [...]`) is still reported.
- **OAuth2 token requests** (a body with `grant_type`): asking for a `scope`
  is what they are for.

| Reported | Not reported |
|---|---|
| `role`, `userRole`, `roleIds`, `roleIDs`, `isAdmin`, `isSuperUser` | `adminNotes` (the head word is *notes*) |
| `permissions`, `permissões`, `scopes`, `tenantId`, `tenantUuid` | the same fields with `readOnly: true` |
| | the same fields in responses only, or in `messages[].role` |

## Why it matters

Mass assignment: many frameworks copy the request body straight into the
database record. If the schema lets the client send `isAdmin` or `role`,
any user can try `{"isAdmin": true}` on their own profile and promote
themselves, or move their record to another tenant.

## How to fix it

Mark the field `readOnly: true`, or remove it from the request schema, and
make the server ignore it on ordinary updates. Change privileges only through
a dedicated operation that checks who is allowed to.

```yaml
role:
  type: string
  readOnly: true
```

## Known limits

Procyon reads the spec. If the server accepts a privileged field the spec
does not document (a hidden `admin` field), only a runtime test can find it;
that is planned for Procyon v0.2.
