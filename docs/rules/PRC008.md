# PRC008 — Unbounded input or output

| | |
|---|---|
| Severity | low |
| OWASP API Security Top 10 | [API4:2023 Unrestricted Resource Consumption](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/) |

## What it catches

Places where the spec lets one request send or receive an unbounded amount
of data:

- a request **string** without `maxLength`: the whole body, a property, or
  the items of a list. Not reported: strings with an `enum`, and formats
  whose length is fixed (`date`, `date-time`, `time`, `uuid`, `ipv4`,
  `ipv6`). `byte` (base64) is reported: it can be any size;
- a request **array** without `maxItems`, including a body that is a list;
- a **`GET` returning an array** with no paging query parameter (`limit`,
  `page`, `per_page`, `page_size`, `size`, `cursor`, `offset`, `first`,
  `after`, `starting_after`, `take`, `top`, `skip`, `page_token`, and
  OData's `$top` / `$skip`), on the operation or its path.

OpenAPI 3.1 nullable types count: `type: [string, "null"]` is a string.
Read-only fields are skipped: the client cannot send them.

It is `low`: it does not fail the build with the default `--fail-on high`.

## Why it matters

Limits are the first defence against requests built to exhaust the server:
a 50 MB "name", a list of ten million IDs, or one `GET` that reads every row
of a table. Declaring them in the spec also lets gateways and generated
servers reject oversized requests before your code runs.

## How to fix it

```yaml
name:
  type: string
  maxLength: 200
ids:
  type: array
  maxItems: 100
```

For lists, add paging parameters with a maximum page size:

```yaml
parameters:
  - name: limit
    in: query
    schema:
      type: integer
      maximum: 100
  - name: cursor
    in: query
    schema:
      type: string
      maxLength: 200
```
