# PRC107 — Predictable ID on a public operation

| | |
|---|---|
| Severity | medium |
| OWASP API Security Top 10 | [API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/) |
| Found by | `procyon test` (runtime) |

## What it catches

An operation the **anonymous** caller reached (a `2xx` with no
credentials), and that needs no login, takes an ID in its path or query
that anyone could guess:

- **a small number**, a whole number below 1,000,000: a script tries every
  one in hours;
- **an id of two kinds of object**: test account A's responses showed the
  same value as the `id` of objects of different kinds, such as a service
  and a car that are both `MQ`. The IDs look random but are counted, each
  table from 1, only written differently (`MQ` is base64 for `1`). Two
  objects are of different kinds when neither has every field the other
  has: a car read in a list and then alone, with more fields, is one kind.

The ID is the one Procyon filled the path or query with, from A's
responses or `test.ids`. An operation needs no login when the spec leaves it
open or marks it `x-procyon-public`: Procyon calls public reads anonymously
(see [PRC106](PRC106.md)). An operation that needs a login is never
reported: [PRC102](PRC102.md) tests whether another account can use its
IDs, and an anonymous `2xx` on it is a [PRC101](PRC101.md).

The finding names the parameter and its value. The evidence is the
anonymous request and the start of its answer.

[PRC007](PRC007.md) reports the same operation from the spec, which cannot
tell a random ID from a counted one. When the objects are public on
purpose, ignore PRC007 there, and PRC107 checks the IDs the server hands
out.

## Why it matters

A public link (an order's tracking page, a booking's confirmation, a shared
document) is protected only by its ID. When the ID is `1`, `2`, `3`, anyone
who sees one link can read all of them, with no account and no limit but
the server's.

## How to fix it

Give objects that anyone can reach without an account IDs nobody can guess:
a random UUID (version 4), or a random token of 128 bits, kept apart from
the database's own row number. Or require authentication for the
operation.

## How to ignore it

If the finding is fine on purpose (a public catalog, where every product is
meant to be found), write an `x-procyon-ignore` on the operation, with the
reason. The finding is still reported, under **Ignored**, and no longer
fails the run. See [ignoring a finding](../ignoring.md).

```yaml
/products/{id}:
  get:
    x-procyon-public: "The shop's catalog"
    x-procyon-ignore:
      - rule: PRC107
        reason: "Every product is listed on the home page anyway"
```

## Examples

Reported: A's `GET /orders` shows `{"id": "1", "trackingId": "1"}`, and the
public `GET /tracking/{trackingId}` answers anyone:

```text
GET /tracking/1       (no Authorization header)
200 {"delivered":false,"item":"Lamp"}
```

Not reported: the same operation with `trackingId: "trk_7Hq2mX9vLp4cW1sD"`,
a number of seven digits or more, or an operation that needs a token.

## Known limits

- Only a field named `id` (or `_id`, `ID`) counts for "an id of two
  kinds": a service's `id` equal to a car's `serviceId` is not seen.
- Two projections of the same object, neither with every field of the
  other (`{id, title}` in one list, `{id, owner}` in another), count as two
  kinds.
- A number of seven digits or more is not reported, though it can be
  counted too; and a small number is reported even when the operation
  shows every object on purpose (ignore it then).
