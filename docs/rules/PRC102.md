# PRC102 — Another account reached A's object

| | |
|---|---|
| Severity | critical |
| OWASP API Security Top 10 | [API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/) |
| Found by | `procyon test` (runtime) |

## What it catches

Broken object level authorization (BOLA): one user reaching another user's
object by putting its ID in the path.

`procyon test` first calls the API as test account **A** and collects the
IDs its responses show (`GET /notes` shows note `1`), then calls the same
operations as test account **B** with A's IDs (`GET /notes/1`). If B gets a
`2xx` **and** the response holds A's ID, it is a finding.

A `2xx` alone is not enough: an API may answer B with B's own data or an
empty list, which is fine. And an ID B's own responses also show is never
counted as A's: it may be shared (a team both belong to).

The finding's evidence is B's request and the start of the response. Tokens
are masked.

Writes and deletes are checked too, after every read (deletes last), so a
destructive request never removes what a later one needs:

- `PUT`, `PATCH` and `POST` on A's object are sent with the request body's
  example from the spec. A reads the object (the `GET` on the same path)
  before and after: if it changed, B changed it. Without such a `GET`, the
  write counts when B's `2xx` answer holds A's ID.
- `DELETE` on A's object: if A can no longer read it afterwards, B deleted
  it. Without a `GET` on the same path, Procyon cannot tell, and says so in
  a note.

An operation that needs a request body the spec gives no example for is
listed under **Notes**.

## Why it matters

It is the most common API vulnerability (OWASP API1). A spec cannot show it:
the operation is authenticated, and the missing check ("is this object
yours?") is a line of server code. Anyone with an account can walk the IDs
(`/notes/1`, `/notes/2`, …) and read everything.

## How to fix it

On the server, load the object and check that it belongs to the caller (or
that the caller may see it) before returning it. Answer `404`, not `403`, so
the response does not confirm that the ID exists. Prefer doing the check in
one place (a query scoped to the caller: `WHERE id = ? AND owner_id = ?`)
over a check in each handler.

## How to ignore it

If the finding is fine on purpose, write an `x-procyon-ignore` on the operation,
with the reason. The finding is still reported, under **Ignored**, and no
longer fails the run. See [ignoring a finding](../ignoring.md).

```yaml
/articles/{id}:
  get:
    x-procyon-ignore:
      - rule: PRC102
        reason: "Articles are readable by every signed-in user"
```

## Examples

Reported: A's `GET /notes` shows note `1`, and

```text
GET /notes/1          (as B)
200 {"id":"1","owner":"alice","title":"Groceries",...}
```

Not reported: the same request answered `404`, or `200` with B's own note
(`{"id":"3","owner":"bob"}`), or `200 []`.

## Known limits

- IDs come from A's responses (or `test.ids` in `.procyon.yaml`). An
  operation whose path parameters cannot be filled is listed under
  **Notes**.
- A response that holds A's object without its ID (no `id` field echoed) is
  missed.
- A write whose example body equals what A's object already holds changes
  nothing, so it is not seen.
