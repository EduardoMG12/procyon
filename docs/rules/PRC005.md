# PRC005 — Response returns a secret

| | |
|---|---|
| Severity | high |
| OWASP API Security Top 10 | [API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/) |

## What it catches

A field in a response schema whose name says it holds a secret. Every schema
an operation can return is checked: nested objects, array items,
`allOf`/`oneOf`/`anyOf`, `additionalProperties` and `$ref`s. A schema shared by
several operations is reported once, where the property is written (see
[ignoring](../ignoring.md) for ignores on one of those operations).

Two kinds of secret:

| Kind | Words (English and Portuguese) | Reported in |
|---|---|---|
| Never returned | password, passwd, passphrase, senha, secret, segredo, private key, chave privada | any response |
| Issued once | token, API key, access key | `GET` responses only |

Tokens and API keys are how authentication works: a login (`POST`) returns a
token, creating a key returns the key. What must never happen is reading one
back later, which is what a `GET` returning it allows.

### How names are matched

Names are split into words: `userPassword`, `password_hash`, `api-token`,
`APIKey` and `senhaUsuario` become *user password*, *password hash*,
*api token*, *api key*, *senha usuario*. A name matches when:

- it contains a listed word whole, or its plural (`apiKeys`, `tokens`,
  `senhas`);
- the word right **before** it does not make it a paging cursor or a
  page-bound token: `nextPageToken`, `continuationToken`, `syncToken`,
  `csrfToken` are not credentials;
- the word right **after** it does not describe the secret instead of
  holding it: `passwordPolicy`, `tokenExpiresAt`, `apiKeyId`,
  `secretName`, `senhaValidade`. Only that next word counts, so
  `senhaEmTextoPlano` is still a password.

Booleans (`passwordSet`, and OpenAPI 3.1's `type: [boolean, "null"]`) are
never secrets. A property that is a `$ref` is reported where the property is
written, not at the shared schema it refers to.

| Reported | Not reported |
|---|---|
| `userPassword`, `password_hash`, `passwordHash`, `tokenData` | `passwordPolicy`, `passwordUpdatedAt` |
| `accessToken`, `api-token`, `APIKey`, `apiKeys` (in a `GET`) | `tokenExpiresAt`, `tokenType`, `apiKeyId`, `nextPageToken` |
| `senhaUsuario`, `senhaEmTextoPlano`, `privateKey`, `clientSecrets` | `tokenizer`, `secretary` (not the whole word) |
| | `passwordSet`, `hasPassword` (booleans) |

## Why it matters

Whoever can read the response gets the secret, and responses travel far:
server and proxy logs, caches, browser developer tools, mobile apps, error
trackers. A password hash can be cracked offline; a token read back from a
listing lets one user act as another.

## How to fix it

Remove the field from the response schema. Check passwords and secrets on
the server, and return only what the client needs (for example
`hasPassword: true`).

## Known limits

Matching is by name. A secret in a field called `value` is not found, and a
non-secret field called `secret` (a book's "secret" chapter) is reported. Both
are rare; report either as a false negative or false positive issue.
