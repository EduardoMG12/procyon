# PRC006 — Personal data returned without authentication

| | |
|---|---|
| Severity | high |
| OWASP API Security Top 10 | [API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/) |

## What it catches

A response field holding personal data in an operation anyone can call: no
security requirement of its own or inherited. Marking the operation public
(`x-procyon-public`) does not silence it: it says the operation is meant to
be open, which makes exposing personal data through it worse.

Personal data, by field name (English and Portuguese, accents ignored):
email, phone/telefone/celular, CPF, RG, SSN, passport/passaporte, national
or tax ID, address/endereço, birth date/data de nascimento, first, last and
full name, surname/sobrenome. Names are matched the same way as in
[PRC005](PRC005.md): whole words, plurals, and not when the next word
describes the data (`emailTemplate` still matches, `addressId` does not).
Booleans such as `emailVerified` are never personal data.

## Why it matters

Whatever an anonymous operation returns, anyone can collect, for every
record they can reach, with a script. Exposing personal data this way breaks
privacy laws (GDPR, LGPD) and feeds phishing and account takeover.

## How to fix it

Require authentication for the operation, and return personal data only to
callers allowed to see it. If the operation must stay public, remove the
personal fields from its response.

## Examples

Reported:

```yaml
/profiles/{username}:
  get:
    responses:
      "200":
        content:
          application/json:
            schema:
              properties:
                email:
                  type: string
```

Not reported: the same operation with a `security` requirement.
