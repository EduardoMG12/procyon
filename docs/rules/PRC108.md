# PRC108 — Another account's list shows A's objects

| | |
|---|---|
| Severity | critical |
| OWASP API Security Top 10 | [API1:2023 Broken Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/) |
| Found by | `procyon test` (runtime) |

## What it catches

A list or search operation that hands one account the objects of another:
a `GET /customers?phone=…` that ignores its filter and returns every
customer, or a `GET /orders` that returns every account's orders instead of
the caller's.

For every list or search operation test account **A** read (a `GET` whose
answer is a JSON array), `procyon test` calls it again as test account
**B**. A required filter is filled with **B's own** value, taken from B's
responses (B's username in `GET /me`), never A's: a search that honours its
filter then returns only B's objects, and one that ignores it returns
everyone's. When an item of B's answer is one of **A's** objects, it is a
finding: the operation leaked A's data into B's list. An item is A's when
both hold:

- it holds a value that marks A: A's identity, what A's single-object
  reads (`GET /me`) showed and B's did not, at least 4 characters long and
  not `true` or `false`, the same values that count for [PRC102](PRC102.md).
  A short number such as `2` (A's user id) is never a mark: a car model or
  a quantity in B's own item can be `2` too;
- A's own answer to the same list shows that item too: an item with the
  same `id` that holds the same value. B's own order sent to A's phone
  number holds A's phone, but it is B's order, not A's.

The finding names the value of A's that B's answer held, the item that held
it, and where A's reads showed it.

This is where a value B saw in a list stops being only a reason to skip the
[PRC102](PRC102.md) test of an object and becomes a finding of its own. If
B's own list already showed it, B seeing it in a list is no leak.

## Why it matters

A missing owner scope on a list is broken object level authorization in
bulk: where [PRC102](PRC102.md) is one object at a time (`/orders/1`,
`/orders/2`, …), a leaking list or search hands over everyone's objects in
a single call, with no IDs to walk. A filter applied *instead of* an owner
scope (`WHERE phone = ?` rather than `WHERE owner_id = ? AND phone = ?`) is
the common cause.

## How to fix it

On the server, scope every list query to the caller
(`WHERE owner_id = ?`), and apply any filter on top of that scope, never
instead of it. A search is a filter over the caller's own objects, not over
the whole table.

## How to ignore it

If the list is public on purpose (a catalogue every account may read),
write an `x-procyon-ignore` on the operation, with the reason. The finding
is still reported, under **Ignored**, and no longer fails the run. See
[ignoring a finding](../ignoring.md).

```yaml
/catalogue:
  get:
    x-procyon-ignore:
      - rule: PRC108
        reason: "The product catalogue is the same for every account"
```

## Examples

Reported: A's `GET /me` shows `"username": "alice"`, and B's own search
still returns alice's rows,

```text
GET /notes-search?owner=bob          (as B)
200 [{"id":"1","owner":"alice",...},{"id":"3","owner":"bob",...}]
```

Not reported: the same search scoped to the caller, which answers B only
its own rows (`[{"id":"3","owner":"bob",...}]`), a list with no value
that marks A's objects (a menu of `{id, name}` every account shares), or
B's own items that happen to hold one of A's values:

```text
GET /me                              (as A)
200 {"id": 2, "phone": "5550001"}

GET /vehicles                        (as B; A's list has only vehicle 5)
200 [{"id": 7, "model": {"id": 2}}]               2 is too short to tell

GET /orders                          (as B; A's list has only order 4)
200 [{"id": 6, "phone": "5550001"}]               A's phone, in B's order 6
```

## Known limits

- The oracle is A's identity: the values A's single-object reads
  (`GET /me`) showed and B's did not. Without such a read, Procyon has no
  mark for A's objects, and a leaking list cannot be told from a shared
  one. A's identity values shorter than 4 characters (a numeric user id)
  are not used, so a list whose items show A only by such a value is not
  reported.
- Items are matched with A's list by their top-level `id`. Items with no
  `id` match any item of A's list that holds the same value, so B's own
  item holding A's value is then reported.
- A required filter B has no value of its own for (no field of that name in
  B's responses) is not tested: a note says so, since filling it with A's
  value would test [PRC102](PRC102.md), not this.
- An operation the anonymous caller could already read is a
  [PRC101](PRC101.md) or public, not a PRC108: if anyone may read the list,
  B reading it is not the finding.
