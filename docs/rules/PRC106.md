# PRC106 — Public operation returned personal data

| | |
|---|---|
| Severity | high |
| OWASP API Security Top 10 | [API3:2023 Broken Object Property Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/) |
| Found by | `procyon test` (runtime) |

## What it catches

An answer the **anonymous** caller got (a `2xx` with no credentials) holds
a field whose **name** says it is personal data and whose **value** has
that kind's shape:

| Kind | Names (as PRC006) | Shape of the value |
|---|---|---|
| e-mail address | `email`, `e_mail`, `customerEmail`, ... | `name@domain.tld` |
| phone number | `phone`, `telephone`, `cellphone`, `mobileNumber`, `telefone`, `celular` | 8 to 15 digits, with spaces, `-`, `.`, `()` and a leading `+` |
| national ID | `cpf`, `rg`, `ssn`, `socialSecurityNumber`, `passport`, `passaporte`, `nationalId`, `taxId` | 6 to 14 digits, with `.`, `-`, `/` and spaces, and at most 3 letters (`12.345.678-X`, `AB123456`) |

Both must agree. `orderNumber: "11987654321"` looks like a phone number but
is not named like one; `phone: null`, `email: ""` and `cpf: "n/a"` are
named like personal data but hold none. Names follow PRC006's exceptions:
`supportEmail` is the company's, `emailVerified` is about the e-mail.

Every answer the anonymous caller gets is checked: from an operation the
spec leaves open, and from one that requires authentication but answered
anyway (then also [PRC101](PRC101.md)), and from every **public read**: a
`GET` marked `x-procyon-public` is called anonymously for this rule. Being
public says the operation is meant to be open, not that anything it shows
is. Public writes (a login) are not called.

A value the anonymous caller **sent in the same request**, in the JSON
body or the query, is not reported when the answer shows it back: a
sign-up that answers `{"merchant": {"email": "merchant@example.com"}}` to
the e-mail it was sent tells the caller nothing new. Any other personal
value of the same answer still is.

Each field is one finding, wherever it is in the answer and however many
objects of a list hold it. The finding names the field by its place in the
answer, property names joined by dots and lists left out (`reviews.email`),
the same way an ignore names it. The evidence is the anonymous request and
the start of its answer, with every personal value masked (`****`).

## Why it matters

Whatever an operation returns to anyone, anyone can collect, for every
record they can reach, with a script. PRC006 reads the spec; this rule reads
what the server really sends, including fields the spec never mentions.
Exposing personal data this way breaks privacy laws (GDPR, LGPD) and feeds
phishing and account takeover.

## How to fix it

Leave the field out of what callers without credentials get (a public page
of reviews needs the author's first name, not their e-mail), or require
authentication for the operation.

## How to ignore it

Some personal data is public on purpose: a business's page shows the
business's own phone. Ignore **that field**, with the reason, and every
other personal field of the same answer is still reported. The field must
be in the operation's response schema. See [ignoring a finding](../ignoring.md#one-field-of-a-response).

```yaml
/shop:
  get:
    x-procyon-public: "The shop's page, shown to every visitor"
    x-procyon-ignore:
      - rule: PRC106
        field: phone
        reason: "The shop's own phone, published on purpose"
```

An ignore without `field` covers every PRC106 finding of the operation.
When the spec describes the field, `procyon lint` reports it too
([PRC006](PRC006.md)), and an ignore of PRC006 cannot name a field yet: it
covers the operation.

## Examples

Reported, twice (`reviews.email` and `reviews.phone`):

```text
GET /shop             (no Authorization header)
200 {"name":"Lamp \u0026 Desk","reviews":[{"author":"Alice","email":"****","orderNumber":"20261031001","phone":"****","text":"The lamp is lovely"}]}
```

Not reported: the same review with only `author`, `text` and
`orderNumber`, or the same answer to a request that needed a token.

## Known limits

- Only e-mail addresses, phone numbers and national IDs are reported. An
  address, a birth date or a person's name has no shape that tells it from
  any other text, so PRC006 (by name, in the spec) is the only check for
  them.
- A value is judged by its shape, not checked: a CPF with a wrong check
  digit is still reported, and a phone number written in words is not.
- Only JSON answers are read.
- A value is left out when it equals one the request sent, wherever the
  answer shows it: if a lookup by e-mail (`GET /users?email=ana@...`)
  answers another user's record that happens to hold the same e-mail, that
  e-mail is not reported (the record's other personal fields are). A value
  sent in the path (`/users/{email}`) is not compared.
