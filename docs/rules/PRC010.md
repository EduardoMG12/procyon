# PRC010 — Admin operation uses only the default security

| | |
|---|---|
| Severity | medium |
| OWASP API Security Top 10 | [API5:2023 Broken Function Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa5-broken-function-level-authorization/) |

## What it catches

An authenticated operation under an administrative-looking path whose
security is exactly that of some regular (non-admin) operation: same
alternatives, same schemes, same scopes, in any order. It does not matter
whether the requirement is inherited from the spec's default or repeated on
every operation.

A path is administrative when one of its segments, split on anything that is
not a letter or digit, contains the word `admin`, `internal`, `debug` or
`management`, or its plural: `/admin/users`, `/orgs/{org}/admins`,
`/internal/metrics`, `/debug-tools/cache`. `/administrators-guide` is not,
and neither are parameters: `/users/{admin_id}` names a user.

An operation is not reported when its requirement is named for admins:
every alternative asks for a scheme or a scope whose name holds one of the
same words, in any case style (`superAdmin`, `AdminApiKey`, `admin_key`,
`oauth: [orders:admin]`). That holds even when a few regular paths use the
same requirement, such as a detailed status page guarded by `superAdmin`:
the name says who it is for. An alternative without such a name lets
regular users in, so `[{superAdmin: []}, {bearer: []}]` is still compared.

Operations with no authentication at all are left to PRC001.

## Why it matters

If an admin operation asks only for "a logged-in user", any customer with an
account may be able to call it. Broken function level authorization (calling
functions meant for another role) is one of the most common ways APIs are
abused, and the spec is where the intended difference should be written down.

## How to fix it

Give the operation a requirement of its own that only administrators meet,
and enforce it on the server:

```yaml
/admin/orders:
  get:
    security:
      - oauth: [orders:admin]
```

If the operation really is for every user, rename the path so it does not
look administrative.

## How to ignore it

If the finding is fine on purpose, write an `x-procyon-ignore` on the operation,
with the reason. The finding is still reported, under **Ignored**, and no
longer fails the run. See [ignoring a finding](../ignoring.md).

```yaml
/admin/users:
  get:
    x-procyon-ignore:
      - rule: PRC010
        reason: "The admin API is only reachable from the VPN"
```

## Examples

Reported (`/admin/users` inherits the default):

```yaml
security:
  - bearer: []
paths:
  /admin/users:
    get: ...
```

Not reported (`/admin/orders` asks for an admin scope):

```yaml
paths:
  /admin/orders:
    get:
      security:
        - oauth: [orders:admin]
```

Not reported (`superAdmin` also guards `/status/details`, but its name says
it is for admins):

```yaml
paths:
  /status/details:
    get:
      security:
        - superAdmin: []
  /admin/tenants:
    get:
      security:
        - superAdmin: []
```

## Known limits

Procyon cannot see what the server enforces. If the default token already
carries roles that the server checks, the finding is a reminder to document
that in the spec, for example with a scope.

An admin word anywhere in a segment counts, so some paths where the word
means something else are reported: Lambda's
`.../functions/{FunctionName}/runtime-management-config` (a function's runtime
update setting), Zoom's `.../sip_trunk/internal_numbers` (phone numbers).
Kubernetes' `/apis/internal.apiserver.k8s.io/...` is reported too: it is an
API group meant for the API servers, but its access is decided by RBAC
roles, which the spec does not show. These paths have the same shape as
`/debug-tools`, which is administrative, so telling them apart would need to
know what each word means in each API. Ignore the finding on such an
operation.

Names are trusted: a scheme called `superAdmin` that every user can meet
hides the finding, and an admin-only scheme with no admin word in its name
(`staffKey`) that also guards a regular path is still reported. An
all-lowercase name is one word, as in paths: `superadmin` holds no admin
word, `superAdmin` and `super_admin` do.
